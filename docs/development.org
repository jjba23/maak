In systems where ~maak~ is already installed, a good way to compile from source and test all program functionality is a pure shell:

#+begin_src shell
guix shell --pure -f guix.scm \
     bash coreutils util-linux-with-udev guile -- \
     maak --list

# Run the project tests
guix time-machine --channels=channels.scm -- \
     shell -f guix.scm --pure -- \
     maak test
#+end_src

Before anything is installed, the launcher under ~scripts~ runs this checkout's own sources inside the environment ~manifest.scm~ declares:

#+begin_src shell
guix shell -m manifest.scm -- ./scripts/maak --list
guix shell -m manifest.scm -- ./scripts/maak test
guix shell -m manifest.scm -- ./scripts/maak man
#+end_src

The suite has a second entry point of its own, ~scripts/maak-test~, and it is the one to reach for when the thing you are changing is the command line itself:

#+begin_src shell
./scripts/maak-test
#+end_src

* Tests

The tests live under ~test/veritas/unit~ and are written with [[https://codeberg.org/jjba23/veritas][Veritas]]. ~maak test~ runs them, by way of ~scripts/maak-test~, which is bash and guile and never loads this checkout's library before the suite does. The direction is deliberate: the thing that runs the tests must not be the thing under test, so a change that breaks `(maak main)` — a parenthesis, a lambda list, a module that will not compile — still gets a suite run and a report instead of a command line that will not start.

The script also picks the environment, in this order, and says which one it chose:

1. ~guix shell -m manifest.scm~, which pins the interpreter, Veritas and the tools the integration specs run;
2. ~nix develop~, the project's flake, for a machine without Guix;
3. the ~guile~ already on ~PATH~, when it can load ~(veritas runner)~.

~MAAK_TEST_ENV=guix|nix|plain~ picks one outright, which is what a container or a CI job wants when it must not fall back to whatever is installed or whatever the machine is not. The same run by hand, in the manifest's environment, is:

#+begin_src shell
VERITAS_TEST_MODULE=veritas VERITAS_TEST_TOP_DIR=test \
  VERITAS_TEST_TYPE=unit VERITAS_RUN_BENCHMARKS=false \
  guix shell -m manifest.scm -- \
  guile -L ./src -L ./test -c '((@ (veritas runner) run-tests))'
#+end_src

That has to be *this* checkout's maak, not the one an installed ~maak~ was built with. The Maak file beside it may ask for modules a released library does not have, and the mismatch shows up as ~no code for module (maak ...)~, which reads like a missing file rather than as a version problem. The launcher under ~scripts~ falls back to the sources beside it, so the checkout's own maak is one command away.

Two kinds of spec sit in that directory, and the difference is what each one can see. Most of them call ~main~ in process with the output ports captured, which is how a test asserts on what a user reads while keeping a run cheap. What that cannot show is anything that belongs to the process rather than to the call: the exit status an operating system sees, which of the two streams a line went to, and the argument grammar of ~scripts/maak~ itself, which is what turns a command line into the Guile invocation ~main~ is handed. Those are what ~test/veritas/unit/integration.scm~ is for, running the launcher as a real subprocess. A suite run is the two together; nothing else starts the launcher, and nothing else reads the library the way a caller does.

The fixtures those tests use — a module with exports and one without, a Maak file with failing tasks for the keep-going flags, and a directory holding a Maak file of its own — live under ~test/maak/fixtures~ and are deliberately kept out of the directory the runner scans.

Two specs check the tree rather than the library, and they are why a change to the packaging or to the guide does not need a reviewer with a good memory:

- ~test/veritas/unit/version.scm~ compares every copy of the version — the RPM
  spec, the Arch recipe, the manual page, the installation page and the newest
  Debian changelog entry — with ~maak-version~. It found the Arch recipe two
  releases behind and the changelog six.
- ~test/veritas/unit/guide.scm~ resolves every ~file:~ link in the README, the
  news and the pages under ~docs/~, checks that every ~::#anchor~ names a
  ~CUSTOM_ID~ in the page it points at, and that every page under ~docs/~ is
  linked from ~docs/index.org~. A page nobody lists is a page nobody finds.

Three things are worth knowing when adding a test, because two of them fail quietly rather than loudly:

- A case has to *evaluate to an assertion*, which is a procedure of one validation client. A bare ~assert-*~ call is one, and so is a ~let~ whose last form is one. A body that ends in ~(delete-file ...)~ is not: the case becomes no case at all, and the test passes without checking anything. Cleanup therefore belongs in a ~#:after~ hook, or in the ~after~ thunk of a ~dynamic-wind~ around the assertion, or before the assertion is built.
- One assertion per case. A case is the value a form evaluates to, so an assertion wrapped in a body of several forms — a ~let~ around five ~assert-*~ calls, say — is evaluated while the file loads and then dropped: only the *last* form of the body is the case that runs and can fail. The four before it still run, but nothing reads their verdict, so they cannot fail the run. Write one assertion per form and give each one the setup it needs; a run of the CLI costs milliseconds, which is cheaper than a test that cannot fail.
- Anything left directly in a ~suite~, outside any ~test~, is treated as a case of the suite, and its result is read as though it were an assertion: the run then dies with "could not read assertion success from unknown type". A parenthesis that closes a ~test~ a line too early is enough to do it.

The first two fail quietly, and nothing catches them for you: the run exits 0 and a test that asserted nothing passes exactly where one that asserts does. The only sign is in the report, which prints the value of every case under the test it belongs to — a test with no line under it ran no case at all, and a case showing one value where two assertions were written means one of them was never read. Read the report, and prefer a test that can fail to a count of tests that passed.

* Continuous integration

A push to ~trunk~ runs ~.github/workflows/ci.yml~, which hands Byggsteg the tasks ~maak-test~ and ~maak-deploy~ through the reusable workflow of [[https://github.com/jjba23/byggsteg-github][byggsteg-github]], and a run is green when the suite is.

A pull request against ~trunk~ runs ~.github/workflows/pull-request.yml~, which hands Byggsteg ~maak-test~ and nothing else. It is a =pull_request_target= workflow, and that is deliberate: GitHub reads that file from ~trunk~ rather than from the pull request, so a patch that edits ~.github/workflows/~ has those edits ignored -- it cannot add a step, change the task list, or name a secret. The run is given a read-only token, and only the two credentials the bridge signs in to Byggsteg with are passed to it, named one by one instead of with =secrets: inherit=. What a patch still controls is the code under test: the daemon clones the branch named in the workflow, runs ~maak test~ there in a container, and nothing of the patch runs on the runner.

Both workflows pin the reusable bridge to a release rather than to a branch, so a repository that publishes a new release is a change somebody makes here.

CodeQL is ~.github/workflows/codeql.yml~, an advanced setup whose languages are written down: =actions=, =javascript-typescript=, =python= and =ruby=, all scanned without a build, on push, on pull request, and weekly. Java and Kotlin are not scanned: the Java extractor resolves dependencies through Gradle, and ~contrib/intellij~ does not configure yet.

* Documentation

The guide is the pages under ~docs/~: one topic each, linked from the
[[file:index.org][documentation index]], with the whole set written in Org. The
page that owns a feature is the page a change to it edits, and a flag or an
environment variable is also written into the manual page.

The technical Guile API documentation is generated from the sources with ~maak docs~ and published here:

https://jointhefreeworld.org/api-docs/maak/index.html

The manual page lives in ~man/maak.1~, is installed with the program, and is previewed by ~maak man~. ~maak --help~ and ~resources/help.txt~ carry the same option reference.

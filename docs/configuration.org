maak is configured three ways, in increasing order of precision: command-line flags, environment variables, and Scheme parameters you set lexically inside a task.

* Environment variables

| Variable          | What it does                                                        |
|-------------------+---------------------------------------------------------------------|
| ~MAAK_ENV_FILE~   | Environment file(s) to read, ~:~-separated, when ~-e~ is not given.  |
| ~MAAK_LOAD_PATH~  | Extra Guile load path entries, ~:~-separated.                        |
| ~MAAK_NO_BANNER~  | Set to ~1~ to skip the greeting banner.                             |
| ~MAAK_DEBUG~      | Set to ~1~ to print the Guile backtrace on error.                   |
| ~MAAK_WATCH_INTERVAL~ | How often ~--watch~ looks at the tree, in seconds (1 by default). |
| ~MAAK_CC~         | The C compiler for ~(maak cc)~; falls back to ~CC~, then ~cc~.        |
| ~MAAK_CXX~        | The C++ compiler for ~(maak cc)~; falls back to ~CXX~, then ~c++~.    |
| ~MAAK_AR~         | The archiver for ~(maak cc)~; falls back to ~AR~, then ~ar~.          |
| ~MAAK_PKG_CONFIG~ | The pkg-config program; ~pkg-config~ by default.                    |
| ~MAAK_CARGO~      | The cargo program for ~(maak cargo)~; falls back to ~CARGO~, then ~cargo~. |
| ~MAAK_RUSTUP~     | The rustup program; falls back to ~RUSTUP~, then ~rustup~.          |
| ~MAAK_UV~         | The uv program for ~(maak python)~; falls back to ~UV~, then ~uv~.  |
| ~MAAK_UVX~        | The uvx program; falls back to ~UVX~, then ~uvx~.                   |
| ~MAAK_PYTHON~     | The interpreter ~(maak python)~ runs; falls back to ~PYTHON~, then ~python3~. |
| ~MAAK_PACKAGE_MANAGER~ | The frontend package manager: ~npm~, ~pnpm~, ~yarn~, or a wrapper such as ~"corepack pnpm"~. |
| ~MAAK_MAVEN~      | The Maven program for ~(maak maven)~; falls back to ~MAVEN~, then ~mvn~. |
| ~MAAK_GRADLE~     | The Gradle program for ~(maak gradle)~; falls back to ~GRADLE~, then ~gradle~. |
| ~MAAK_EMACS~      | The Emacs program for ~(maak elisp)~; falls back to ~EMACS~, then ~emacs~. |
| ~MAAK_ELEVATE~    | The program that answers ~#:sudo?~: ~doas~, ~sudo~, or one with options. |
| ~MAAK_CONTAINER_ENGINE~ | The container engine: ~podman~ or ~docker~.                  |
| ~MAAK_COMPOSE~    | The Compose program, for example ~podman-compose~ or ~docker compose~. |
| ~MAAK_FETCH~      | The downloader ~download~ uses: ~curl~ or ~wget~.                   |

#+begin_src shell
MAAK_ENV_FILE=".env:.env.local" MAAK_NO_BANNER=1 maak -- build
#+end_src

~CC~, ~CXX~ and ~AR~ are honoured by the C/C++ helpers unless ~MAAK_CC~,
~MAAK_CXX~ or ~MAAK_AR~ names a compiler, and a value may carry a wrapper such
as ~"ccache gcc"~.  ~CFLAGS~, ~CXXFLAGS~, ~CPPFLAGS~, ~LDFLAGS~ and ~LDLIBS~
are *not* read automatically: a task says which one reaches which command with
~(environment-flags "CFLAGS")~, because a flag that belongs to a compile and one
that belongs to a link are not the same decision.  See
[[file:c-and-cpp.org][C, C++ and Make/Automake]].

~MAAK_CARGO~ and ~MAAK_RUSTUP~ are read the same way, and their values may carry
a wrapper or a toolchain -- ~"cargo +nightly"~ is the usual one.  See
[[file:rust-and-cargo.org][Rust and Cargo]].

~MAAK_MAVEN~, ~MAAK_GRADLE~ and ~MAAK_EMACS~ are read the same way too, and a
value may carry flags.  A checkout's ~mvnw~ or ~gradlew~ is not chosen through
the environment: ~maven-wrapper-command~ and ~gradle-wrapper-command~ answer
with it, and a task opts in with ~parameterize~.  See
[[file:maven-and-gradle.org][Maven, Gradle and the JVM]] and
[[file:emacs-lisp.org][Emacs Lisp packages]].

~MAAK_UV~, ~MAAK_UVX~ and ~MAAK_PYTHON~ are read the same way, so a value may
carry flags (~"uv --preview"~).  See [[file:python.org][Python, uv and pyproject]].

~MAAK_PACKAGE_MANAGER~ is read once, when the library loads, because it decides
which *verbs* the frontend helpers use and not only which program they run: it
is the answer ~(package-manager-kind)~ gives.  Without it, the answer comes from
the lock file in the directory maak runs in -- ~package-lock.json~ for npm,
~pnpm-lock.yaml~ for pnpm, ~yarn.lock~ for yarn -- and an empty directory means
npm.  A value may carry a wrapper, as in ~"corepack pnpm"~, and the last word is
the manager.  A task that wants another manager for one call writes
~(parameterize ((package-manager "pnpm")) ...)~.  See
[[file:frontend.org][Frontend projects: npm, pnpm and yarn]].

A project with no ~maak.scm~ may keep its tasks in ~maak.yaml~, ~maak.yml~,
~maak.toml~ or ~maak.json~ instead; the variables below are read for a task file
exactly as they are for a Maak file.  See
[[file:task-files.org][Task files in JSON, TOML and YAML]].

* Parameters: dry-run, quiet, banner, escalation

Dry-run and quietness can be set globally with ~-n~ / ~-q~, but they are also Scheme parameters that can be overridden in lexical scope. That gives you precise control, and it is what makes destructive code safe to exercise in tests:

#+begin_src scheme
(define (fmt)
  "Format Scheme source files according to the Guix style guide."
  (syscall "ls") ;; this will run
  ;; this will not
  (parameterize ((dry-run? #t)
                 (quiet? #f))
    (delete-file-recursively "tmp")
    ($ '("find . -maxdepth 8 -name '*.scm'"
         "-type f -exec guix style -f {} \\;")
       #:verbose? #t)))
;; it will print instead of running
;; [DRY-RUN]: rm -rfv tmp
;; [DRY-RUN]: find . -maxdepth 8 -name '*.scm' -type f -exec guix style -f {} \;
#+end_src

~elevation-command~ is the same kind of parameter. It holds the program ~#:sudo?~ runs — detected as ~doas~ or ~sudo~ when maak starts — and can be pinned for one call, which is how a test keeps its expected command line independent of the machine:

#+begin_src scheme
(parameterize ((elevation-command "doas -n"))
  ($ '("install -d /var/lib/maak") #:sudo? #t))
#+end_src

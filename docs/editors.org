* Shell completions

maak ships completions for Bash, Zsh and Fish. In a directory with a Maak file, type ~maak~, a space, then TAB, and the task names appear. The completion scripts read the current Maak file and extract task names from it.

The scripts live in ~scripts/~ and, in most situations, are installed for you. If you installed by hand, load them yourself — these variables are handy if you run Guix:

#+begin_export html
<details>
  <summary>See a Bash example of manual completion load</summary>
#+end_export

#+begin_src shell
#!/usr/bin/env bash
maak_bin_install_dir=$(which maak)
maak_install_dir=$(realpath "${maak_bin_install_dir}")
maak_bin=$(dirname "${maak_install_dir}")
maak_store=$(dirname "${maak_bin}")
maak_completions="${maak_store}/share/bash-completion/completions/maak"

# Load Maak auto-completions
if [[ -f "${maak_completions}" ]]; then
  source "${maak_completions}" || true
fi
#+end_src

</details>
#+end_export

* Editor integrations

Every editor that can run a process gets an integration, and they all read the same task list from the same helper. [[file:../contrib/README.org][=contrib/=]] holds them, and the helper they share is =contrib/bin/maak-tasks= — a small Guile script that reads the Maak file the way maak and maak.el do, and prints its tasks as JSON:

- only what the =#:export= list names, or every procedure when it exports nothing;
- each docstring, which is the task's documentation;
- each lambda list, so an editor can ask for a required argument, show the default of an optional one, take several words for a rest argument and leave a keyword argument alone — maak's command line cannot pass one;
- the line the definition starts on, so a task can be visited where it is written.

The file is read, never evaluated.  Put the helper where your shell finds it, once, for every editor below:

#+begin_src shell
install -m 755 contrib/bin/maak-tasks ~/.local/bin/maak-tasks
#+end_src

| Editor       | What you get                                                          | Where                                    |
|--------------+-----------------------------------------------------------------------+------------------------------------------|
| Neovim       | =:Maak= picks with =vim.ui.select= and runs in a terminal tab.          | [[file:../contrib/nvim/README.org][contrib/nvim]]       |
| Vim          | =:Maak= picks from a numbered menu and runs in a terminal tab.          | [[file:../contrib/vim/README.org][contrib/vim]]        |
| VS Code      | The command palette, and =Tasks: Run Task=, running in a terminal.      | [[file:../contrib/vscode/README.org][contrib/vscode]]     |
| IntelliJ     | *Tools → Run maak Task…*, output in the Run tool window.                | [[file:../contrib/intellij/README.org][contrib/intellij]]   |
| Zed          | A generated =.zed/tasks.json=, because Zed reads tasks from a file.       | [[file:../contrib/zed/README.org][contrib/zed]]         |
| Sublime Text | Quick panels, and the run in a Sublime build panel.                    | [[file:../contrib/sublime/README.org][contrib/sublime]]     |
| Helix        | =maak-picker= for =:sh=: fzf, the argument prompts, and a terminal.      | [[file:../contrib/helix/README.org][contrib/helix]]       |

They all list the tasks the file defines, show the docstring, prompt for the arguments, run the task where its output belongs, visit a definition, and dry-run one with =maak -n=.  Neovim, Vim and VS Code also repeat the last run, and Neovim and Vim complete task names for =:MaakRun=.

The prompts are maak.el's, because they are what maak's grammar allows: a required argument is asked for, an optional one left blank is not passed at all (and neither is anything after it), a rest argument takes any number of words, and a keyword argument is never asked for because a string never becomes a keyword.

* The REPL workflow

A REPL is an interactive environment connected to your console, your running application, your compiler — and it gives you superpowers as an engineer 🦸🏼. Lisp dialects, and Guile in particular, have excellent support for this. The author's own setup is [[https://guix.gnu.org/][Guix]], [[https://www.gnu.org/software/emacs/][Emacs]], [[https://git.sr.ht/~abcdw/emacs-arei][Arei/Ares]] and [[https://github.com/vspinu/sesman][sesman]]: an infinitely extensible editor experience, miles ahead of traditional IDEs 🐂.

It fundamentally changes the development workflow by eliminating the slow /edit, save, compile, run/ cycle:

- *Incremental development.* Write, test, inspect and evaluate one function — or one line — at a time, with immediate feedback and no full rebuild.
- *Powerful debugging.* Forget ~print~ statements and restarts: pause, inspect objects, change values, redefine a broken function on the fly, in any environment.
- *Fast prototyping.* Load a library and call its functions to learn it, which is much faster than reading documentation alone.

Integrated into your editor, you can execute any piece of code (a line, a selection, a file) with a keyboard shortcut and see the result instantly.

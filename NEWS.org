*[Released]*

** v0.19.0 (2026-11-14)

The three items the vision document listed as "in scope and not built yet" are
built, and they rest on one decision: what a task is, is data — and every
consumer reads the same description of it.

*** Added

- `maak --list --json` prints the task listing as one versioned JSON object:
  the file, the root it sits in, and every task with its docstring, the line its
  definition starts on, what it needs first, an example invocation and the
  arguments maak binds, each with its kind, its default and the prose that
  describes it.  Nothing else is printed, so the output is the JSON and only the
  JSON.  `--json` on its own is an error, since it describes a listing rather
  than asking for one.
- `task-metadata!` declares what a task is beyond its docstring, and the
  vocabulary is exactly three fields: `#:depends`, a quoted list of tasks that
  must have finished before this one starts; `#:hidden?`, which keeps a task out
  of the listings while leaving it runnable; and `#:example`, one invocation to
  show a reader.  A fourth field is a decision about what a task is rather than a
  key a project adds, which is why the list is closed.
- A dependency orders a run and nothing else: the sequential runner and `-j`
  both put a task after the ones it needs, a task named twice runs once, and a
  cycle or a dependency that names no task is an error before anything starts.
  Nothing is remembered between runs, so ordering has not become a cache by the
  back door.
- The prose for an argument lives in the docstring under a line reading `Args:`,
  one line per argument, which is the convention this repository's own
  docstrings already kept.  `maak --list --json` and
  `contrib/bin/maak-tasks --preview` give it beside the argument it belongs to,
  which is what an editor prompts with.
- `maak --list` says what a task needs first, under its documentation, and
  leaves out a task that asked to be hidden.
- `test/veritas/unit/listing.scm`, `test/veritas/unit/metadata.scm` and
  `test/veritas/unit/json.scm`, plus cases in `integration.scm` that compare the
  two readers byte for byte and run a dependency-ordered `-j`.

*** Changed

- `contrib/bin/maak-tasks` is a front end for maak's own reader, `(maak tasks)`,
  instead of a second parser of the same file.  Its modes, its exit statuses and
  its JSON all stay, and a task is now described once in this repository rather
  than once per integration.  It needs maak's libraries, which it finds in a
  checkout or wherever an installed maak put them.
- The fixture the helper and the guide are tested against has one task of every
  shape, a hidden task, a dependency and a written-out argument section.
- A parameter is no longer a task.  `(define build-args (make-parameter '()))`
  returns something callable, and `maak-proc?` counted it as one, so a value a
  task reads appeared in the listing as a task with no documentation.

*** Fixed

- `packaging/debian/changelog` carries the released version again; it had been
  five releases behind, which the suite had been failing on.

** v0.18.0 (2026-11-10)

Zed's task list stops being a snapshot: =maak-zed= writes it again when the
Maak file changes, and the generated file carries the task that does the
writing.

*** Added

- =contrib/zed/maak-zed=: =sync= writes =.zed/tasks.json= beside the nearest
  =maak.scm=, and =watch= writes it again whenever that file changes.  Neither
  rewrites a file whose content is already right, so Zed is not made to reload
  its task list for nothing.
- The generated Zed file ends with a =maak: watch tasks= task, which runs that
  watch in a terminal of its own: start it once and the spawn list follows the
  Maak file for as long as the editor is open.
- =contrib/test/maak-zed.sh= covers syncing from a subdirectory, the no-op
  rewrite, regeneration after an edit, a Maak file that does not read, and the
  watch, including a task file deleted underneath it.

*** Changed

- =maak-tasks= refuses a Maak file that does not read to the end instead of
  listing the tasks before the mistake.  A file looks like that halfway
  through an edit, and the short list was worth showing only until something
  wrote it out; =maak-zed= now leaves the task file it wrote alone until the
  Maak file reads again.

** v0.17.0 (2026-11-10)

Seven editors, one reader of the Maak file: the integrations in =contrib/= now
cover Zed and Sublime Text as well, and every one of them got the commands that
turn a task list into a working day — completion, dry runs and the last task
run.

*** Added

- =contrib/=, a directory of maak integrations for Neovim, Vim, VS Code,
  IntelliJ, Zed, Sublime Text and Helix.  They all read the task list from
  =contrib/bin/maak-tasks=, a Guile script that reads a Maak file the way
  maak.el does — =#:export=, docstrings and lambda lists — without evaluating
  it, and prints it as JSON.  =contrib/README.org= says how to install one.
- Dry runs wherever a command runs: =:MaakDryRun= in Neovim and Vim,
  =Maak: Dry Run Task= in VS Code, =Tools → Dry-run maak Task…= in IntelliJ,
  =--dry-run= for the Helix picker, and =maak -n= in the generated Zed tasks.
- Task-name completion for =:MaakRun= in Neovim and Vim, from the same Maak
  file the picker reads.
- =:MaakLast= in Neovim and Vim, and =Maak: Run Last Task= in VS Code, which
  repeat the last run without the picker or the prompts.
- =maak-tasks --zed= writes the =.zed/tasks.json= Zed reads, because Zed has no
  hook that could ask for a task list at runtime.
- =contrib/test/maak-tasks.sh= checks the helper against a fixture with one
  task of every shape: exports, docstrings, each argument kind, a redefined
  task, and every output mode.

*** Changed

- =docs/editors.org= describes the seven integrations, the shared helper and
  the prompts they have in common, instead of only Emacs and the shell
  completions.

** v0.15.0 (2026-11-09)

A packaging release: the Arch recipe builds, a release keeps every copy of the
version in step, and two specs watch the things that used to rot in silence.

*** Added

- ~test/veritas/unit/version.scm~ compares every copy of the version — the RPM
  spec, the Arch recipe, the manual page, the installation page and the newest
  Debian changelog entry — with ~maak-version~, so a release whose copies were
  not rewritten fails the suite instead of shipping a package two versions old.
- ~test/veritas/unit/guide.scm~ resolves every ~file:~ link in the README, the
  news and the pages under ~docs/~, checks each ~::#anchor~ against the
  ~CUSTOM_ID~s of the page it points at, and checks that every page under
  ~docs/~ is linked from the index.
- The Arch page of the guide says how to build the package now, instead of
  asking for a patch.

*** Fixed

- ~packaging/arch/PKGBUILD~ unpacked into the wrong directory: ~makepkg~
  extracts the tag's archive as ~maak-VERSION~, and the recipe changed into
  ~maak~, so it could not have built at all. Its ~pkgver~ said 0.12.2 and its
  checksum was that archive's, and it fetched from a host the release tags are
  not pushed to.
- ~packaging/debian/changelog~ was six releases behind, at 0.8.3.

*** Changed

- ~maak sync-version~ writes the Arch ~pkgver~ as well, so the recipe follows a
  release like the RPM spec and the manual page do. The changelog entry and the
  Arch checksum stay in a person's hands, and
  [[file:docs/project.org::#releasing][the releasing page]] says why.

** v0.14.1 (2026-11-08)

A housekeeping release: the licence, the pipeline and the documentation are
brought in line with the sibling projects, and a release is no longer published
from a floppy disk.

*** Changed

- The project is licensed under the *MIT License*, the same terms as =ggg=,
  =iter-vitae=, =veritas= and =bewaking=. =COPYING= became =LICENSE=, every
  source, script, test and packaging file carries an
  =SPDX-License-Identifier: MIT= header, and the licence fields of the Nix
  derivation, the Guix package, the RPM spec, the PKGBUILD and the Debian
  copyright file all say MIT.
- =maak --version= prints =License: MIT=, so a script that reads that line sees
  the same answer the files give.
- The README is a landing page now: it leads with the point that a task is a λ,
  and the manual moved into =docs/=, one topic per page, indexed by
  =docs/index.org=. Every page keeps the text it had; only the headings moved.
- CI is a GitHub Actions workflow that calls the same Byggsteg pipeline the other
  projects use, so =.woodpecker/byggsteg.yaml= is gone.
- =maak sync-version= writes the version into =docs/installation.org= rather than
  the README, which no longer carries a copy of it.

*** Removed

- =resources/maak-icon.png=, the floppy-disk mascot, and the copy of it embedded
  in =resources/maak-banner.svg=. The banner keeps its terminal window, wordmark
  and prompt.

*** Added

- =NEWS.org=, this file.

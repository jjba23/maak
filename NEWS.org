All notable changes to this project are documented in this file, one section per
release tag. The version itself is written once, in =src/maak/version.scm=.

This project adheres loosely to [[https://semver.org/spec/v2.0.0.html][Semantic Versioning]].

*[Unreleased]*

*[Released]*

** v1.1.1 (2026-11-21)

A formatting release: `(maak frontend)` is laid out the way a `sift` pass over
the tree expects, so the module stops being the one file that changes whenever
the tree is formatted.  No command line the helpers build changed, and the spec
that asserts them is byte for byte the same.

*** Changed

- `(maak frontend)` writes its `cond` and `case` clauses with the brackets
  `sift format` produces, which is a whitespace and bracket change and nothing
  else.  `frontend-add`'s docstring keeps the `@example` that shows `#:dev?`,
  which the pass had dropped.

** v1.1.0 (2026-11-21)

The task list is a table now: every docstring starts in the same column, and
the shape of the listing is a choice rather than a constant.  And `maak test`
no longer needs a working maak to test maak.

*** Added

- `--list` is a table now, and it has layouts.  The default listing aligns every
  docstring on one column -- a heading naming the file and how many tasks it
  holds, then one entry a task with its name emphasised, its documentation in
  that column, and what it needs to have finished first underneath -- so a
  listing of forty tasks reads down one edge instead of restarting at every
  name.  `--list=STYLE` picks another shape: `long` adds the example a task
  declares, `plain` is the `name: documentation` blocks the table replaced,
  `names` is one task name per line for a script or a picker, and `json` is the
  description `--list --json` prints.  `--list-width N` folds a docstring into N
  columns; without it a docstring is printed as it was written, so a code sample
  or an `Args:` table a task laid out stays laid out.
- `tasks-table` in `(maak maak)`: the aligned listing as one string, for a task
  that prints its own menu.  `list-tasks` grew `#:style`, `#:width` and
  `#:file` to render it.
- `color?` in `(maak dsl)`, a parameter that turns ANSI styling off for a whole
  run.  `NO_COLOR`, set to anything but the empty string, is what it reads by
  default, so `maak --list` and a dry run reach a file or a CI log plain.
- [[file:docs/ai.org][Maak files and AI assistants]]: what to ask maak instead of
  guessing (`--list --json`, `--plan --json`, `explain`, and the static reader
  for a file that does not compile yet), the few rules a Maak file is reviewed
  against, the traps a first draft falls into, and a block to paste into a
  project's `AGENTS.md`, `CLAUDE.md` or rules directory.  The limits an answer
  should not cross are on the same page: `#:depends` orders a run and never skips
  one, a declared dependency is run with the arguments the task was given, and a
  task that guards on a file an earlier task builds cannot pass a dry run.
- `contrib/ai/maak-skill.md`, a skill file for an assistant: the module header,
  the ten rules, the vocabulary a task may call grouped by area, the Guile forms
  a Maak file actually uses, and the loop that checks the work — `maak --list`,
  then `maak -n`, then `maak --plan`, then the real run.  Plain Markdown with no
  front matter, so it can be pasted into a context or added to a project's
  instructions; `contrib/ai/README.org` says how, and says it changes in the same
  commit as the options and helpers it names.
- `llms.txt`, a map of the guide for a tool: the two versioned JSON objects to
  read instead of guessing, then the page that answers each question, as raw
  URLs.

*** Changed

- `--list` prints the listing and nothing else: the greeting banner and the
  `Loading tasks from:` line are gone, because the listing carries its own
  heading, and the environment-file lines an environment file used to announce
  are silenced for a listing the way they already were for `--plan`.
- `--list=json` and `--list=names` are the same requests as `--list --json` and
  `maak-tasks --names`, spelled as one word.
- `maak test` runs `scripts/maak-test`, which is bash and guile and never loads
  this checkout's library before the suite does.  The direction is the point:
  the thing that runs the tests must not be the thing under test, so a change
  that breaks `(maak main)` now gets a suite run and a report instead of a
  command line that will not start.  It also picks the environment -- the
  manifest under Guix, the flake under Nix, or the guile already on `PATH` --
  says which one it chose, and takes `MAAK_TEST_ENV=guix|nix|plain` when it must
  not choose for itself.

*** Fixed

- A listing no longer announces the environment file it read before printing
  itself, which used to land between the heading and the first task.

** v1.0.0 (2026-11-17)

The first release that promises something: the public surface is frozen and
written down, and every place that names this project points at the repository
that is alive.

*** Added

- [[file:docs/stability.org][What 1.0 freezes]]: the standard the version number is about -- the exported
  bindings of the installed modules, the command line, the environment
  variables, the Maak file's shape and the two versioned JSON descriptions --
  the things explicitly left out of it, and how a deprecation is announced,
  kept and removed.
- ~packaging/opensuse/maak-rpmlintrc~, the suppressions the RPM build always
  tried to copy and never had.
- ~(maak sift)~, re-exported by ~(maak maak)~: ~sift-argv~ builds any of sift's
  subcommands (the dialect, the style, the line length, the checkers, the
  filters and the rest as keywords), ~sift~ runs one, and ~sift-status~
  returns the exit status rather than flattening it -- 0 clean, 1 findings, 2 a
  usage error or a file that cannot be parsed.  ~sift-exit-meaning~ names which
  of the three a code was; ~sift-format~, ~sift-check~, ~sift-lint~ and
  ~sift-ci~ are the gates, and each raises with a hint that says which of the
  two a failure was.  ~sift-files~ finds the Lisp files under a directory,
  sorted and pruned, with ~#:exclude~ for the fixtures a project leaves
  unformatted, using the walk ~(maak watch)~ already had rather than a second
  one.  The program is ~MAAK_SIFT~, then ~SIFT~, then ~sift~.
- ~(maak veritas)~: ~veritas-env~ is the four ~VERITAS_*~ assignments the runner
  reads, ~veritas-test-argv~ is the guile invocation as words,
  ~veritas-shell-command~ is the same words with the expression quoted for a
  manifest shell, and ~veritas-test~ runs the suite and fails the task when it
  does not pass.
- ~watch-relist~ in ~(maak watch)~: re-runs a listing now and on every change,
  reporting a broken edit instead of ending the watch.
- ~docs/sift.org~ and ~docs/veritas.org~.

*** Changed

- The homepage is ~https://github.com/jjba23/maak~ everywhere: ~maak
  --version~, the help screen, the manual page, the installation page, the
  README, the guide's community page, ~guix.scm~, ~default.nix~, the RPM spec
  and its OBS ~_service~, the Debian control and copyright files, the Arch
  recipe's ~url~, the Homebrew formula and the VS Code extension.  Codeberg
  archived its copy of this repository on 2026-11-08, so a link there can no
  longer take a patch or an issue, and OBS was still fetching its source from
  it -- where a tag newer than that archive cannot exist.
- The manual page names ~MAAK_SIFT~.

*** Fixed

- ~maak rpm-build~ stopped on ~cp packaging/opensuse/maak-rpmlintrc~, a file
  the tree did not have.  The suppressions exist now, and rpmlint is given
  them with ~-r~ rather than trusted to find them beside the RPM it checks.

*** Verification

- The Veritas suite is green -- no failing case -- run under ~guix shell -m
  manifest.scm~.  The sift and Veritas specs assert the argv builders, the
  three exit statuses, the walk that finds the files and the quoting a
  manifest shell needs; a stand-in sift runs as a real process through the
  launcher, which is what covers ~sift-status~ reading a status and passing
  sift's own output on.
- The version's copies agree with ~maak-version~ in the RPM spec, the Arch
  recipe, the Homebrew formula, the manual page, the installation page and the
  newest Debian changelog entry, which the suite compares.
- The checksums of the release archive in the Arch recipe and the Homebrew
  formula are refreshed from the published tag after the push, which is the
  one step no task can take before the archive exists.

** v0.25.0 (2026-11-17)

Python projects get uv and the pyproject they already have, and a frontend
project gets npm, pnpm and yarn behind one set of procedures.

*** Added

- `(maak python)`, re-exported by `(maak maak)`: `uv-argv` builds a uv
  invocation (the program-wide options before the subcommand, the ones the
  project-reading commands take after it, the caller's words last), `uv` runs
  it, `uv-output` returns what a command printed, and `uv-version` returns the
  version uv reports.  `uv-init`, `uv-sync`, `uv-lock`, `uv-run`, `uv-add`,
  `uv-remove`, `uv-tree`, `uv-export`, `uv-build`, `uv-publish`, `uv-venv`,
  `uv-pip` and `uv-python` are one line each, and their arguments are uv's own.
- `uvx-argv` and `uvx` for a tool in a temporary environment, and
  `python-argv`, `python`, `python-module`, `python-output` and
  `python-version` for the interpreter itself, with `-m` and `-I` named
  options rather than words a caller has to remember.
- The pyproject readers: `pyproject-file` names the file (a parameter),
  `pyproject-data` returns the whole document as data, `python-project` the
  `[project]` table, and `python-project-name`, `python-project-version`,
  `python-requires-python`, `python-project-scripts` and
  `python-build-backend` the five facts a task asks for.  A project that leaves
  its version to the build backend is refused by name rather than guessed at.
- The four checks a Python CI runs, through `uv run` so the locked version is
  the one that runs: `python-test` (pytest), `python-lint` (ruff check),
  `python-format` (ruff format) and `python-type-check` (mypy), plus
  `python-check`, which runs the lint, the type check and the tests in that
  order.  The words a caller gives replace the default path.
- `(maak frontend)`: `package-manager` is a parameter holding the program the
  checkout pins -- `MAAK_PACKAGE_MANAGER`, or the lock file in the directory
  maak runs in, npm when there is none -- and `package-manager-kind` answers
  which of the three it is, from the last word of the command, so
  `"corepack pnpm"` is pnpm.  `detect-package-manager` reads the lock file from
  a directory named.
- `frontend-argv` builds the command line, with the flag that points a manager
  at a directory spelled as that manager spells it (`--prefix`, `--dir`,
  `--cwd`); `frontend` runs it and `frontend-output` returns what it printed.
- The wrappers that spell out where the three managers disagree:
  `frontend-install`, `frontend-ci` (`npm ci`, `pnpm install
  --frozen-lockfile`, `yarn install --immutable`, and `--frozen-lockfile` on a
  Yarn 1 checkout, told apart by `.yarnrc.yml`), `frontend-add` (with
  `#:dev?`), `frontend-remove`, `frontend-run`, `frontend-exec` (including
  npm's `--`) and `frontend-publish` (including Yarn 2's `yarn npm publish`).
- The conventional scripts: `frontend-build`, `frontend-test`, `frontend-lint`,
  `frontend-format` and `frontend-check`.
- The package.json readers: `package-json-file`, `package-json`,
  `package-name`, `package-version`, `package-scripts`,
  `package-dependencies` and `package-dev-dependencies`.
- `docs/python.org` and `docs/frontend.org`.

*** Changed

- `(maak formats)` reads two TOML constructs it used to refuse: an array or an
  inline table that spans several lines, and an array of tables (`[[name]]`),
  which appends one table per header.  A `pyproject.toml` from a project that
  configures uv is read rather than refused.
- The manual page names the tool variables it was missing: `MAAK_UV`,
  `MAAK_UVX`, `MAAK_PYTHON` and `MAAK_PACKAGE_MANAGER`.

*** Verification

- The Veritas suite is green, with new `python` and `frontend` specs that
  assert the argv builders, the pyproject and package.json readers, the dry-run
  commands and the error messages, from manifests and stand-in programs the
  specs write themselves.  The `formats` spec covers the two TOML constructs
  the reader gained, including the refusal that keeps a table and an array of
  tables apart.
- `contrib/test/maak-tasks.sh` still passes all 43 checks.

** v0.24.0 (2026-11-16)

Java and Kotlin projects get the Maven and Gradle lifecycle as argv, and an
Emacs Lisp package gets its batch checks and the conventions it is expected to
keep.

*** Added

- `(maak maven)`, re-exported by `(maak maak)`: `maven-argv` builds a Maven
  invocation (pom and settings files, profiles, `-D` properties, threads, the
  CI flags and the lifecycle goals), `maven` runs it through `run`,
  `maven-output` returns a report, and `maven-clean`, `-validate`, `-compile`,
  `-test`, `-package`, `-verify`, `-install`, `-deploy`, `-site`,
  `-dependency-tree` and `-effective-pom` are one line each.
- `(maak gradle)`: `gradle-argv` builds a Gradle invocation (project and build
  files, `-P` properties, `-x` exclusions, the daemon, cache, parallel and
  rerun flags, warning and console modes, workers), `gradle` runs it,
  `gradle-output` returns a report, and `gradle-assemble`, `-build`, `-check`,
  `-test`, `-clean`, `-run`, `-tasks`, `-dependencies`, `-projects` and
  `-publish` are one line each.
- `maven-wrapper-command` and `gradle-wrapper-command`: the `mvnw` or `gradlew`
  a checkout pins, checked when a task runs; `maven-wrapper?` and

- `(maak elisp)`: `emacs-batch-argv` builds a `--batch` invocation (load paths,

- `elisp-byte-compile` (with `#:warnings-as-errors?`), `elisp-checkdoc` and
  `elisp-ert` (with ERT's selector as a Lisp expression) are the three checks a

- The practice readers: `elisp-header`, `elisp-package-version`,
  `elisp-package-requires`, `elisp-provides`, `elisp-feature`,
  `elisp-lexical-binding?` and `elisp-footer?`, plus `elisp-practices`, which
  answers with the conventions a file is missing, and
  `elisp-practices-ok?`.  `elisp-version` reports the Emacs it is running.
- `docs/maven-and-gradle.org` and `docs/emacs-lisp.org`.

*** Changed

- The manual page names the tool variables it was missing: `MAAK_CARGO`,
  `MAAK_RUSTUP`, `MAAK_MAVEN`, `MAAK_GRADLE` and `MAAK_EMACS`.

*** Verification

- The Veritas suite is green, with new `maven`, `gradle` and `elisp` specs that

** v0.23.0 (2026-11-16)

Rust projects get the helpers Cargo already needs, and a project that wants a
task list rather than a language can write one in JSON, TOML or YAML.

*** Added

- `(maak cargo)`, a module of Cargo and Rust helpers, re-exported by
  `(maak maak)`.  `cargo-argv` builds the command line -- global options before
  the subcommand, the subcommand's own after it, the arguments last -- `cargo`
  runs it through `run`, and `cargo-output` returns its standard output.
  `cargo-build`, `cargo-check`, `cargo-test`, `cargo-run`, `cargo-bench`,
  `cargo-fmt`, `cargo-clippy`, `cargo-doc`, `cargo-clean`, `cargo-fetch`,
  `cargo-update`, `cargo-publish` and `cargo-install` are one line each over
  it, and their arguments are cargo's own.
- `cargo-metadata` parses `cargo metadata` into a string-keyed alist;
  `cargo-package`, `cargo-package-version`, `cargo-package-names`,
  `cargo-binaries`, `cargo-target-directory` and `cargo-artifact-path` answer
  the questions a release task asks.  The queries run even in a dry run,
  because they read the project rather than changing it.
- rustup helpers: `rustup-argv`, `rustup`, `rustup-output`,
  `rustup-active-toolchain`, `rustup-toolchains`, `rustup-install`,
  `rustup-target-add` and `rustup-component-add`.  The programs are parameters
  honoured from `MAAK_CARGO`/`CARGO` and `MAAK_RUSTUP`/`RUSTUP`, and a value may
  carry a wrapper or a toolchain (`"cargo +nightly"`).
- `(maak formats)`, readers for a documented subset of JSON, TOML and YAML, and
  `(maak declarative)`, which reads a task list written in one of them.  A task
  file is discovered when `maak.scm` is absent -- `maak.yaml`, `maak.yml`,
  `maak.toml` or `maak.json`, in that order -- and `-f` names any of them.
  `--list`, `--list --json`, `--plan`, `--watch`, `explain` and `-j` work as
  they do for a Maak file, and `maak-tasks` finds the same candidates.
- The data schema is `doc`, `command` or `commands`, `depends`, `env`,
  `directory`, `hidden`, `example` and `allow-failure`.  A list of strings is
  an argv run without a shell; a string is a shell line.  An unknown key, an
  unsupported construct or a task with no command is an error, never a guess.
- `docs/rust-and-cargo.org` and `docs/task-files.org`.

*** Changed

- maak looks for a task file when `./maak.scm` is absent, and the greeting says
  "Loading tasks from" rather than "Loading tasks from Maak file".
- `contrib/bin/maak-tasks` searches the same candidates and reads a data file,
  so the editor integrations keep working.
- The manual page and the command-line page describe the widened default.

*** Verification

- The Veritas suite is green, with new `formats`, `declarative` and `cargo`
  specs and two integration cases that run a YAML task file through the
  launcher.
- `contrib/test/maak-tasks.sh` still passes all 43 checks.

** v0.22.0 (2026-11-15)

C and C++ projects can move a Makefile into tasks without losing the pieces
they rely on: a compiler and linker invocation, pkg-config's flags, a static
library, parallel object compilation and an explicit up-to-date check.

*** Added

- `(maak cc)`, a module of C and C++ build helpers, re-exported by
  `(maak maak)`.  The compiler and archiver are parameters read from
  `MAAK_CC`/`CC`, `MAAK_CXX`/`CXX` and `MAAK_AR`/`AR`, and a value may carry a
  wrapper such as `"ccache gcc"`.
- `compile` and `compile-argv` compile one source with includes, defines,
  flags, a language, a standard, `-fPIC` and `-MMD -MP`.  `compile-objects`
  compiles a list, with `#:jobs` for concurrent compilers and
  `#:incremental?` for skipping objects newer than their sources.
- `link` and `link-argv` link objects into a program or a shared library, with
  libraries, library paths, `#:flags` before the objects (LDFLAGS) and
  `#:link-flags` after them (LDLIBS and pkg-config's libs), plus `#:shared?`,
  `#:static?` and `#:soname`.  `static-library` writes an `ar rcs` archive.
- `object-file`, `up-to-date?` and `environment-flags`: the object path for a
  source, the explicit target/input check a task uses to skip a compile, and
  the words of `CFLAGS`, `CPPFLAGS`, `LDFLAGS` or `LDLIBS` when a task asks
  for one.  Nothing is rebuilt on a timestamp unless the task says so.
- `pkg-config-cflags`, `pkg-config-libs`, `pkg-config-exists?` and
  `pkg-config-version`, with the program taken from `MAAK_PKG_CONFIG` or the
  `pkg-config-command` parameter.  They run even in a dry run, because
  pkg-config reads the system, so `--plan` shows the flags a compile would
  really use.
- `install-file` and `install-directory` in `(maak shell)`, the `install` a
  Makefile's install target reaches for, with parent directories and modes.
- `docs/c-and-cpp.org`: a C project, a C++ project, pkg-config, explicit
  incremental builds, a Make/Automake mapping table, and what maak does not do.

*** Changed

- The `link` helper in a Maak file is the C linker rather than Guile's POSIX
  `link`; `(maak cc)` declares the replacement so importing it does not warn.
  A task that needs the POSIX call should import it under another name.

*** Verification

- The Veritas suite is green, with a new `cc` spec that asserts the argv
  builders, the shell-word parsing of a pkg-config stand-in, the explicit
  up-to-date check, the environment flag reader and both install helpers.
- `contrib/test/maak-tasks.sh` still passes all 43 checks.

** v0.21.0 (2026-11-15)

A run is inspectable before and after it happens: a typed plan, a watch with no
watcher to install, an explanation of the composition and the environment, and
a bundle that carries its Guile.

*** Added

- `maak --plan TASK` runs the task with dry-run semantics and prints the typed
  plan it describes instead of a transcript: each command, its argv or shell
  line, the directory it would run in, the environment it was given, whether it
  would be elevated and whether it would be started in the background.  The
  recorder sits in the helpers that build every command -- `run`, `$`,
  `syscall`, `capture`, `run-pipeline` and `guix repl` -- so a task's own
  Scheme decides what the plan says.  Nothing is executed.
- `maak --plan --json TASK` prints the same plan as one versioned object.  A
  task's own printing goes to standard error, so a task that logs does not
  corrupt the object a CI job archives.  `--plan` records one task at a time and
  refuses `-j` rather than silently ignoring it.
- `maak --watch TASK` runs the task now and again whenever the tree changes.
  The tree is `git ls-files --cached --others --exclude-standard` in a checkout
  and a walk that skips repository and cache directories otherwise.  Each run
  reloads the Maak file, re-reads the environment files from the environment the
  watch started with, and starts in the directory the watch started in, so an
  edit to a task or a `.env` takes effect and a task's changes do not leak into
  the run after it.  A failing run is reported and the watch continues.
  `MAAK_WATCH_INTERVAL` sets the interval and accepts fractional seconds.
- `maak explain TASK`, also spelled `--explain`, prints what the task calls and
  what calls it, what it declared with `task-metadata!`, the load path, the
  elevation command and a per-variable report of the environment files: the
  process environment wins, and otherwise the first file that sets a name wins,
  because later files do not override.  The call graph is read from the Maak
  file's text, so a call built with `apply`, passed as a procedure or produced
  by a macro is not in it, and the guide says so.
- `(maak bundle)` builds a self-contained artefact of a project's automation on
  top of `guix pack`: a generated package installs the Maak file and a launcher,
  propagates maak, Guile and the packages the caller names, and produces a
  relocatable tarball, a squashfs image or a docker image tarball.  `#:load?`
  loads a docker pack with the container helper, and `#:maak-package` points at
  a project's own build of maak.  This repository's `maak package-bundle` task
  uses it.

*** Changed

- The repository's own `hot-reload` and `dev` tasks use `watch-tree` instead of
  a hand-rolled `watchexec` invocation, so `watchexec` is no longer part of the
  development manifest.
- The Bash, Zsh and Fish completions know `--plan`, `--watch` and `--explain`,
  and the help screen, manual page and guide document the new modes and the
  bundle helper.

*** Verification

- The Veritas suite is green, with new specs for the plan, the watch, the
  explanation and the bundle: the plan is parsed as JSON, the environment
  precedence is asserted rather than assumed, and the call graph is checked on
  the project's own Maak file.
- `contrib/test/maak-tasks.sh` still passes all 43 checks, including the two
  that compare `maak --list --json` with the editor helper byte for byte.

** v0.20.0 (2026-11-15)

Seven editor integrations that prompt with the task author's own words, a task
list that does not go stale under the cursor, and a Homebrew formula.

*** Added

- Argument prose reaches every prompt.  A docstring's `Args:` section says what
  to type for an argument, and Neovim, Vim, VS Code, Sublime Text, IntelliJ and
  the Helix picker now show it beside the argument's name.  The helper's
  `--words` mode ends each line with that prose, so a shell integration prompts
  with the same words an editor does.
- A picker shows what a task declares about itself: the tasks it needs first in
  every integration, and the example invocation where the editor has a second
  line for it (VS Code's quick pick detail, Sublime Text's quick panel).
- Neovim forgets its cached task list as soon as `maak.scm` changes: an
  `fs_event` watcher on the project directory and a `BufWritePost` autocommand
  both invalidate it, and `require("maak").refresh()` and the
  `User MaakTasksChanged` event let a plugin react to the change.
- VS Code caches the list it reads and drops it when `maak.scm` is changed,
  created or deleted; its task provider fires `onDidChangeTasks`, so
  `Tasks: Run Task` and the pickers show the new list without reloading the
  window.
- `maak-tasks --executable NAME` and `maak-zed --executable NAME` name the maak
  a generated Zed task runs, and `MAAK_EXECUTABLE` does the same for `maak-zed`
  and the Helix picker.
- A Homebrew formula, `packaging/homebrew/Formula/maak.rb`, builds maak from the

** v0.19.0 (2026-11-14)

The three items the vision document listed as "in scope and not built yet" are
built, and they rest on one decision: what a task is, is data — and every
consumer reads the same description of it.

*** Added

- `maak --list --json` prints the task listing as one versioned JSON object:
  the file, the root it sits in, and every task with its docstring, the line its
  definition starts on, what it needs first, an example invocation and the
  arguments maak binds, each with its kind, its default and the prose that
  describes it.  Nothing else is printed, so the output is the JSON and only the
  JSON.  `--json` on its own is an error, since it describes a listing rather
  than asking for one.
- `task-metadata!` declares what a task is beyond its docstring, and the
  vocabulary is exactly three fields: `#:depends`, a quoted list of tasks that
  must have finished before this one starts; `#:hidden?`, which keeps a task out
  of the listings while leaving it runnable; and `#:example`, one invocation to
  show a reader.  A fourth field is a decision about what a task is rather than a
  key a project adds, which is why the list is closed.
- A dependency orders a run and nothing else: the sequential runner and `-j`
  both put a task after the ones it needs, a task named twice runs once, and a
  cycle or a dependency that names no task is an error before anything starts.
  Nothing is remembered between runs, so ordering has not become a cache by the
  back door.
- The prose for an argument lives in the docstring under a line reading `Args:`,
  one line per argument, which is the convention this repository's own
  docstrings already kept.  `maak --list --json` and
  `contrib/bin/maak-tasks --preview` give it beside the argument it belongs to,
  which is what an editor prompts with.
- `maak --list` says what a task needs first, under its documentation, and
  leaves out a task that asked to be hidden.
- `test/veritas/unit/listing.scm`, `test/veritas/unit/metadata.scm` and
  `test/veritas/unit/json.scm`, plus cases in `integration.scm` that compare the
  two readers byte for byte and run a dependency-ordered `-j`.

*** Changed

- `contrib/bin/maak-tasks` is a front end for maak's own reader, `(maak tasks)`,
  instead of a second parser of the same file.  Its modes, its exit statuses and
  its JSON all stay, and a task is now described once in this repository rather
  than once per integration.  It needs maak's libraries, which it finds in a
  checkout or wherever an installed maak put them.
- The fixture the helper and the guide are tested against has one task of every
  shape, a hidden task, a dependency and a written-out argument section.
- A parameter is no longer a task.  `(define build-args (make-parameter '()))`
  returns something callable, and `maak-proc?` counted it as one, so a value a
  task reads appeared in the listing as a task with no documentation.

*** Fixed

- `packaging/debian/changelog` carries the released version again; it had been
  five releases behind, which the suite had been failing on.
- A run describes the file it loaded.  `load` adds to the module `(maak)` rather
  than replacing it, and a task is looked up in the module's public interface,
  so a process that loaded a second Maak file answered with the union of both --
  which nothing did before the suite started loading several files in one run.

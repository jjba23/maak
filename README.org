* Core features

Instead of learning a limited DSL, you can leverage your existing Lisp skills to define tasks, manage data, and automate your workflows with ease. Define functions, manipulate lists, use conditional, create macros—the entire language is at your disposal.

You can also easily call external shell commands and integrate with your existing scripts and tools.

All you will need to do to use Maak is to write a file (by default ~./maak.scm~) where you define your Maak file module and import Maak library:

#+begin_src scheme
(define-module (maak)
  #:declarative? #t
  #:use-module (maak maak))
#+end_src

Then declare some /runnable/ jobs (a.k.a. tasks). Any function can be a task,  with or without arguments:

#+begin_src scheme
(define (hello)
  "Say hello from Maak!"
  (display "Hello from Maak!")
  (display (format #f "~a + ~a = ~a" 3 4 (+ 3 4))))

(define (quick-math x-arg y-arg)
  ;; beware task args come always as strings due to CLI parse
  (let* ((x (string->number x-arg))
         (y (string->number y-arg)))
    (format #t "~a + ~a = ~a" x y
            (+ x y))))
#+end_src

You can now run it:

#+begin_src shell
maak hello
maak quick-math 23 42
#+end_src

* Defining tasks

Any function (with or without arguments) you define in this file becomes a runnable task.

** Task Export & Visibility Rule
- *Open Fallback (No Exports)*: If you do not write an ~#:export~ directive in your module (or leave it empty), Maak is completely "open season": all procedures in the file are treated as runnable tasks.
- *Strict Lock (With Exports)*: If you define anything in your ~#:export~ directive (e.g., ~#:export (quick-math)~), then only the explicitly exported procedures will be treated as tasks. Any other functions become private helper procedures and are completely hidden from the CLI and ~--list~ command.

If no task is passed via command-line, Maak will run the ~default~ task.

Tasks can:
- Run shell commands with the ~$~ helper.
- Print logs with ~log-info~.
- Call other Maak tasks.
- Use any Guile Scheme function you define (or import from a library).
- Some syntactic sugar for working with Guix dev shells and time-machine, e.g.  ~manifest-shell~ and ~program-shell~ as well as ~time-machine-manifest-shell~ and more

⚠️ Beware not to use names for tasks that conflict with names of built-in Scheme functions as this can cause some problems. For example, avoid calling something ~format~ or ~display~, choose something else instead.

You can extend Maak by defining new tasks — just like writing functions in Scheme.

You can also run multiple tasks easily (sequentially) via a comma-separated list :

#+begin_src shell
maak fmt,compile,test
#+end_src

Often it's just cleaner to do it directly in Lisp (Scheme code ) in your Maakfile (where it's also trivial to add concurrent computations)

More advanced examples here and below:

#+begin_src scheme
;; Format Scheme source code files according to the Guix style guide.
(define (fmt)
  (log-info "Format Scheme files using Guix Style")
  ($ '("find . -maxdepth 8 -name '*.scm'"
       "-type f -exec guix style -f {} \\;")
     #:verbose? #t))

;; Display program help screen.
(define (help)
  ($ '("guix shell -f guix.scm -- maak --help")))

;; By default (no task given) run help.
(define (default)
  ($ '("maak --list"))

;; Do some quick math
(define (arithmetics)
  (fmt) ;; call another task first
  (let* ((entries '(1 3 5 7 9))
         (arithmetics (lambda(x) (* x x 3)))
         (some-data (map arithmetics entries)))
    (log-info "Running default task")
    (log-info "Performed some fun arithmetics:\nResult: ~a" some-data)))
#+end_src

* Command Line Interface Options

Maak provides standard CLI options to manage your execution pipeline:

| Short Flag | Long Flag    | Argument | Description                                                          |
|------------+--------------+----------+----------------------------------------------------------------------|
| ~-f~         | ~--file~       | ~FILE~     | Specify the path to the Maak file (defaults to ~./maak.scm~).          |
| ~-C~         | ~--directory~  | ~DIR~      | Change to ~DIR~ before the Maak file is read (repeatable; ~:~-separated allowed). |
| ~-h~         | ~--help~       | None     | Display the help screen and exit.                                    |
| ~-i~         | ~--ignore-errors~ | None    | Keep going after a failure, and let the run succeed anyway.         |
| ~-j~         | ~--jobs~       | ~N~        | Run up to ~N~ tasks at the same time, keeping each task's output together. |
| ~-k~         | ~--keep-going~ | None     | A task that fails does not stop the tasks after it.                  |
| ~-l~         | ~--list~       | None     | List all available tasks in the currently loaded Maak file.          |
| ~-L~         | ~--load-path~  | ~DIR~      | Add ~DIR~ to Guile's load path (repeatable; ~:~-separated allowed).    |
| ~-n~         | ~--dry-run~    | None     | Dry-run mode. Print shell commands instead of executing them.        |
| ~-q~         | ~--quiet~      | None     | Quiet mode. Suppress standard logging, banners, and header outputs.  |
| ~-v~         | ~--version~    | None     | Display the Maak version and exit.                                   |
| ~-e~         | ~--env-file~   | ~FILE~     | Read ~NAME=VALUE~ assignments from ~FILE~ (repeatable; ~:~-separated allowed). |
|              | ~--no-env-file~ | None     | Read no environment file at all, whatever the environment says.      |
|              | ~--no-print-directory~ | None | Do not report the directories ~-C~ changes to.                      |
|              | ~--banner~     | None     | Print the greeting banner (the default; overrides ~MAAK_NO_BANNER~).  |
|              | ~--no-banner~  | None     | Skip the greeting banner, keeping everything else.                   |
|              | ~--debug~      | None     | Print the Guile backtrace on error (same as ~MAAK_DEBUG=1~).           |

A manual page is installed with the program; ~man maak~ shows the same options
without leaving the terminal.

The greeting banner is printed by default.  ~--no-banner~ keeps a run's output
free of decoration, which is what a script wants, and ~MAAK_NO_BANNER=1~ does
the same from the environment.  ~--banner~ turns it back on, which is handy
when the variable lives in a shell profile.

A run names the tasks it is to run, and the words that follow a task are passed
to it as its arguments.  A double-dash decides what the words around it are:

#+begin_src shell
# One task, given the arguments it takes
maak quick-math 23 42

# The same run, with -- setting the arguments apart.  This is how an argument
# that begins with a dash gets through, unread as an option of maak's own
maak quick-math -- -23 42

# Two tasks, as one comma separated word, dry-run and quiet
maak -n -q clean,build

# The same two tasks, one word each: a -- before the first task word begins the
# task list, and every word up to a further -- names a task
maak -n -q -- clean build

# Tasks named one word each, given arguments of their own after that further --
maak -- clean build -- -v
#+end_src

A ~--~ *after* a task word does not change which words are tasks: everything
that follows the first task word is an argument, whether or not it is set
apart.  So ~maak deploy production~ and ~maak deploy -- production~ are the same
run -- the task ~deploy~, given the word ~production~ -- while
~maak -- deploy production~ names two tasks, ~deploy~ and ~production~.  Name
the tasks with ~-t LIST~ / ~--tasks LIST~ instead, and every other word of the
line is an argument.

That is the whole of the grammar, and the two spellings are the only two: a
word never names a task and an argument at once, and a word that happens to
name a task is still an argument when it is not the task list or one of the
words a ~--~ introduces.

When that is what happened, the run says so.  A task handed a word it cannot
take fails with Guile's complaint about arity, and when one of those words names
a task of the same Maak file the failure carries a hint naming both spellings of
the run that was probably meant:

#+begin_src shell
$ maak alpha beta
maak: error: Wrong number of arguments to #<procedure alpha ()>
        hint: `beta' names a task of this Maak file, so alpha received it as an argument.  To run several tasks, name them in one comma separated list (`maak alpha,beta') or one word each after `--' (`maak -- alpha beta'); a task's arguments are the words that follow its name.
#+end_src

** Running several tasks, and from another directory

Four of Maak's switches are Make's, because the situations they answer come up
in any project and not only in a build:

- ~-j~ / ~--jobs N~ runs up to N tasks at the same time.  Each task gets a
  worker of its own, and its standard output and standard error are printed as
  one block, in the order the tasks were named, so a parallel run stays
  readable.  A task that fails stops nothing -- every named task has already
  been started, so ~-j~ has ~--keep-going~ for free -- and the run fails at the
  end with the tasks that did not succeed.  A task that changes the environment
  or the working directory changes its worker's copy, not its neighbours'.
- ~-k~ / ~--keep-going~ keeps going after a task fails.  Every failure is
  reported where it happened, naming the task that raised it, and the run fails
  at the end with the list of tasks that did not succeed.  Without it the first
  failure ends the run, which is what a pipeline of tasks usually wants.
- ~-i~ / ~--ignore-errors~ is the same run with a different verdict: the
  failures are warnings and the run still succeeds.  It is what exercises the
  rest of a pipeline while one step is known to be broken.
- ~-C~ / ~--directory~ changes directory before anything else -- before the
  Maak file is found, before a ~.env~ beside it is read, and before any task
  runs -- and says which directory it entered.

#+begin_src shell
# Run every task of the pipeline, and see all of the failures at once
maak -k -- fmt,lint,test

# Run the independent ones four at a time, each task's output kept in one block
maak -j 4 -- fmt,lint,test

# Run the tasks of another checkout's Maak file
maak -C ../other-project -- build
#+end_src

~-C~ may be repeated, and the directories are entered in the order given, so
~maak -C build -C signatures -- sign~ runs from ~build/signatures~.  A directory
that is not there is an error rather than a quiet fallback, because a task must
never run somewhere it was not asked to.

The directory a run enters is reported, which is what Make's ~-w~ prints; ~--no-print-directory~
is the switch that leaves those lines out, for a run whose output is read by
something other than a person.  ~-q~ asks for that silence too, along with the
rest of what the run would say.

* Environment files

Settings and credentials often live in a file rather than in the environment.
Maak reads one before it loads the Maak file, so the names are already in place
for every task:

1. ~-e FILE~ / ~--env-file FILE~ names a file.  Repeat the flag, or separate
   several files with ~:~, to read more than one:
   #+begin_src shell
   maak -e .env -e .env.local -- deploy
   #+end_src
2. ~MAAK_ENV_FILE~ is read when no flag is given, with the same
   ~:~-separated shape:
   #+begin_src shell
   MAAK_ENV_FILE=".env:.env.local" maak deploy
   #+end_src
3. failing both, the ~.env~ file beside the Maak file is read when it exists.
4. ~--no-env-file~ reads none of them.

The file is a list of ~NAME=VALUE~ lines:

#+begin_src shell
# Comments and blank lines are skipped, and a line without an = is ignored.
DATABASE_URL=postgres://localhost/dev
QUOTED="a value with spaces"
SINGLE='single quoted'
#+end_src

Surrounding quotes are removed, so ~QUOTED~ above holds ~a value with spaces~,
and the rest of the line is taken as it stands: a value keeps its ~=~, its ~#~
and its inner spaces.

A name the environment already has wins, so a file can hold a sensible default
and a one-off ~DATABASE_URL=... maak deploy~ can still point a single run
somewhere else.  Every file that is read is reported, so a run says where its
values came from.

From Scheme, ~load-env-file~ reads one itself and returns the names it set
(~#:override? #t~ when the file should win over the environment), and
~env-file-entries~ reads one without touching the environment at all.

* Load paths: requiring your own modules

A Maak file can be a thin front end over modules that live beside it. Maak puts
the directory of the Maak file itself on Guile's load path, and lets you add
more from three angles:

1. the ~-L~ / ~--load-path~ flag, repeatable or ~:~-separated:
   #+begin_src shell
   maak -L ./lib -L ./src -- build
   #+end_src
2. the ~MAAK_LOAD_PATH~ environment variable, a ~:~-separated list:
   #+begin_src shell
   MAAK_LOAD_PATH="./lib:./src" maak build
   #+end_src
3. from Scheme, inside a task or at the top of the Maak file:
   #+begin_src scheme
   (add-load-path! "./lib")            ;; for the rest of the run
   (with-load-path '("./lib" "./src")  ;; only for the thunk
     (lambda () (use-modules (mylib util))))
   #+end_src

All three feed Guile's own ~%load-path~, so they compose with whatever
~GUILE_LOAD_PATH~ is already set.  ~with-load-path~ restores the path even when
the thunk raises.

One trap worth knowing: whether it is on the load path or not, a ~use-modules~
written *inside a task body* has no effect -- it is expanded where it stands,
not when the task runs.  Import at the top level of the Maak file, as above, or
load a module by name from inside a task:

#+begin_src scheme
(define (report)
  (with-load-path '("./lib")
    (lambda ()
      (let ((util (resolve-module '(mylib util))))
        (log-info "~a\n" ((module-ref util 'format-row) '(1 2 3)))))))
#+end_src

* How ~--list~ lays out docstrings

The docstring of a task is its documentation.  ~maak --list~ prints it in a way
that stays readable no matter how long it is:

- one line prints inline after the name:

  #+begin_src
  build: Compile the project.
  #+end_src

- two lines start inline and align the continuation under the documentation:

  #+begin_src
  build: Compile the project.
         The result lands in ./target.
  #+end_src

- three or more lines become a block, with the name on its own line and every
  line of documentation indented to the same column:

  #+begin_src
  release:
           Bump the version, tag the tree,
           upload the artefacts and then
           push the tag.
  #+end_src

Common source indentation is removed first, so a docstring written inside an
indented procedure still reads flush left.

* Builtins

Every helper below is exported by ~(maak maak)~ and can be called from a task.
They all honour the ~dry-run?~ and ~quiet?~ parameters.

** Shell

Two runners sit at the bottom.  ~run~ takes a program and its arguments as
separate strings and starts it without a shell; ~$~ takes one shell line for
the cases that need one.  Prefer ~run~: a path with a space in it stays one
argument instead of becoming three words.

- ~(run argv)~ -- run a program from a list of strings.  The first string is
  the program, every other one is an argument exactly as written.

  #+begin_src scheme
  (run (list "mkdir" "-p" build-dir))
  (run (list "git" "commit" "-m" message))
  (run (list "npm" "ci") #:dev-null? #t)
  (run (list "guix" "shell" "-m" "manifest.scm" "--" "make" "test")
       #:env '("CI=1"))

  (unless (run (list "git" "diff" "--quiet") #:allow-failure? #t)
    (log-info "the tree is dirty\n"))
  #+end_src

  It accepts the same ~#:env~, ~#:sudo?~, ~#:dev-null?~ and
  ~#:allow-failure?~ keywords as ~$~, and a program that cannot be started
  exits 127, which is reported like any other non-zero exit.  The helpers
  below (~mkdir-p~, ~cp~, ~mv~, ~cat~, ~touch~, ~ln-s~, ~chmod-file~ and
  ~delete-file-recursively~) are built on ~run~, so a path with a space in it
  reaches the program as one argument.

  ~#:expand? #t~ joins the arguments with spaces and hands them to the shell,
  so a wildcard, ~$VAR~ or a leading tilde is expanded the way a shell would.
  It is opt-in because the shell then sees words rather than arguments: a path
  with a space in it becomes several words again.  The file helpers pass the
  keyword through, so ~(delete-file-recursively "build/*.o" #:expand? #t)~
  removes every object file the shell names.

- ~(run-pipeline stages)~ -- run programs one after another with each standard
  output feeding the next standard input, without a shell:

  #+begin_src scheme
  (run-pipeline (list (list "cat" file)
                      (list "grep" "-v" "^#")
                      (list "sort" "-u")))
  #+end_src

  Each stage is an argument list shaped like ~run~'s.  Unlike a shell's ~|~,
  which reports only the last stage, a pipeline reports every stage that
  failed; ~#:allow-failure? #t~ returns ~#f~ instead of raising.

- ~(run argv #:async? #t)~ -- start the program in the background and return a
  *job* record.  Unlike a trailing ~&~, the job has a pid and a status that can
  be waited for:

  #+begin_src scheme
  (define server (run (list "guix" "shell" "--" "run-server") #:async? #t))
  (log-info "server started as ~a\n" (job-pid server))
  ...
  (unless (wait-job server)
    (task-error "the server exited with a failure"))
  #+end_src

  ~job?~, ~job-pid~, ~job-command~, ~job-done?~ (non-blocking), ~wait-job~ (returns
  ~#t~ when the exit code is 0) and ~job-exit-code~ read the job.  ~$~ and
  ~syscall~ return the same record for ~#:async?~, so a background shell line
  can be waited on too; maak forks the process rather than leaving a ~&~ to the
  shell, which is what makes the pid available.

- ~($ parts ...)~ -- run a shell command built from strings, joined by spaces.
  This is the escape hatch, for pipes, redirections, globs, ~$(...)~ and
  ~VAR=value~ prefixes.  The command can be decorated with keyword arguments,
  applied in the order a shell would write them:
  ~[sudo] [env A=1] COMMAND [>/dev/null 2>&1]~.

  #+begin_src scheme
  ($ '("systemctl daemon-reload") #:sudo? #t)
  ($ '("make" "-j4") #:env '("CI=1" "V=1"))     ;; env CI=1 V=1 make -j4
  ($ '("npm ci") #:dev-null? #t)                   ;; npm ci >/dev/null 2>&1
  (define watch ($ '("tsc --watch") #:async? #t))   ;; a job, see wait-job

  (unless ($ '("git diff --quiet") #:allow-failure? #t)
    (log-info "the tree is dirty\n"))
  #+end_src

  ~#:env~ takes an alist (~(("CI" . "1"))~), a list of ~KEY=VALUE~ strings or
  one such string, and the names are set for that command alone.  They go
  through ~env~ rather than as a ~KEY=VALUE~ prefix, which is what lets them
  reach a command running inside a ~guix shell~.

  ~#:allow-failure?~ returns ~#f~ instead of raising when the command exits
  non-zero, so the task is told the command failed and can decide what that
  means; it is the ~cmd || true~ idiom, except that the failure is not hidden
  from the task.  ~#:async?~ starts the command in the background and returns a
  job, and ~#:sudo?~ runs it as root -- both are printed by ~--dry-run~ like
  anything else, so they can be checked before they are really run.

- ~syscall~ -- run one shell line and raise when it exits non-zero; it is ~$~
  without the list of parts.
- ~capture~ -- return a command's output.  A command that exits non-zero raises
  an error naming its exit code instead of returning the empty or partial
  output it produced; pass ~#:allow-failure? #t~ to read that output anyway.
- ~which~, ~command-exists?~, ~require-command~ -- find a program on ~PATH~.
- ~shell-quote~ -- quote a value so a shell reads it as one word.
- ~read-file~, ~write-file~ -- read and write a file from Scheme.
- ~mkdir-p~, ~remkdir-p~, ~delete-file-recursively~, ~cp~, ~mv~, ~cat~,
  ~touch~, ~ln-s~, ~chmod-file~ -- file helpers, all built on ~run~.
- ~with-directory~, ~cd~, ~env-get~, ~env-set!~, ~env-unset!~, ~with-env~,
  ~with-env-vars~, ~home-dir~, ~tmp-dir~, ~load-env-file~, ~env-file-entries~.

** Reporting a failure from a task

A task that fails should read like maak's own errors: one line saying what went
wrong, and a hint saying what to do about it.  ~task-error~ is that, with an
optional format string and its arguments:

#+begin_src scheme
(define (deploy)
  "Deploy the artefact built earlier."
  (task-error "no artefact for ~a" #:args (list "linux-x86_64")
              #:hint "Run `maak build' first."))
#+end_src

~maak deploy~ then prints

#+begin_src
maak: error: no artefact for linux-x86_64
        hint: Run `maak build' first.
#+end_src

and exits non-zero without a backtrace, so a user reads a sentence instead of a
trace.  ~--debug~ (or ~MAAK_DEBUG=1~) brings the backtrace back when the
failure is the program's own fault rather than the project's.  ~raise-maak-error~
is the same mechanism for a message that is already formatted, and
~maak-error?~ recognises either one.

** Pretty multiline strings

Guile has no heredoc, so a long message is a string spanning several source
lines with the source indentation baked in.  These helpers take it back out:

#+begin_src scheme
(text "first line"
      "second line")        ;; => "first line\nsecond line"
(dedent-string indented)      ;; remove the common indentation
(indent-string s #:by 4)      ;; add indentation
(unlines '("a" "b"))          ;; join with newlines
#+end_src

** Guix

- ~manifest-shell~, ~program-shell~ and their ~time-machine-~ variants.
- ~guix-shell~ -- a shell described by a package list.
- ~guix-container~ -- ~guix shell --container~, optionally with ~--network~,
  ~-S~ shares and ~-E~ exposures.
- ~guix-pack~ -- build a ~guix pack~ (docker, squashfs, tarball).

Every one of them takes the same ~#:env~, ~#:sudo?~, ~#:dev-null?~,
~#:allow-failure?~ and ~#:async?~ keywords as ~$~, and passes them to the
command it builds.

** Nix

Mirroring the Guix helpers, for machines that use Nix:

- ~nix-shell~ (classic, ~shell.nix~), ~nix-develop~ (flakes), ~nix-build~,
  ~nix-flake-build~, ~nix-flake-check~, ~nix-run~.

They take the same decorations as the Guix helpers and as ~$~.

** Internationalisation

The gettext workflow, packaged so it does not have to be rewritten per project.
The layout is the conventional one (~DIR/LANG/LC_MESSAGES/DOMAIN.po~):

#+begin_src scheme
(define (i18n)
  "Refresh every translation catalogue."
  (i18n-refresh '(en_US nl_NL es_ES)
                #:dir "po"
                #:textdomain "myproject"
                #:directories '("lib" "app/views")))
#+end_src

- ~i18n-extract~, ~i18n-init~, ~i18n-merge~, ~i18n-compile~ -- the four GNU
  gettext tools.
- ~i18n-init-all~, ~i18n-merge-all~, ~i18n-compile-all~, ~i18n-refresh~ -- the
  same over a list of languages.
- ~i18n-locale-dir~, ~i18n-po-file~, ~i18n-mo-file~, ~i18n-pot-file~,
  ~i18n-source-globs~ -- where the catalogues live.
- ~i18n-translator~, ~i18n-language~ -- load a catalogue and get a translate
  procedure.

* Why write Maak ?

Have you ever found Makefile to be repetitive, lacking expressiveness and having a weird, limited syntax and unexpected arcane behavior?

No fear, *Maak* is here. With the full power of Lisp directly in your command runner/control plane,  easily define functions, data, lists, loop through them, macros, etc. Maak replaces the arcane syntax of Make with the power and elegance of a full-featured functional programming language: GNU Guile Scheme λ.

Maak replaces Make’s runes and mystery with the power and clarity of GNU Guile Scheme λ.

* The Problems with Make

Many developers find GNU Make and related tooling to be at times frustrating and not intuitive, despite being so powerful.

Makefile often contains /repetitive/ code, particularly when dealing with similar targets or file types. You might have to write a separate rule for every single output file, even if the process is exactly the same. The limited syntax makes it difficult to abstract this logic into reusable functions or macros, leading to a lot of copy-pasting.

Make's syntax is a Domain-Specific Language (DSL), not a general-purpose programming language. While it's powerful for its intended purpose of managing dependencies, it's /terrible for anything else/.

Defining variables, using conditionals, or looping over a list of items can be surprisingly clunky and often requires arcane, non-standard constructs.

Make has many "gotchas" that can trip up even experienced users.

* How Maak Innovates

Maak positions itself as a modern infinitely extensible task runner, using the functional programming language  GNU Guile Scheme (a dialect of Lisp). No need for .PHONY recipes here.

Maak gives you the power of Scheme. You're not restricted to a limited, weird syntax. This means you can easily define functions to avoid repetition, create complex data structures (like lists and maps), and use control flow statements (like loops and conditionals) to write much cleaner and more expressive scripts.

Instead of having to learn a new, limited language, you can leverage your existing Lisp knowledge to define tasks, manage data, and automate your workflows. This leads to code that is much easier to read, write, and maintain. For example, you can write a simple loop to process all your source files instead of writing a separate rule for each one.

Maak is designed to be your central control plane. While Make is primarily focused on building software from source, Maak is a general-purpose command runner. This means you can use it for tasks like running tests, deploying applications, or managing your development environment. It's meant to be a more flexible and powerful alternative for all your project's automation needs.

* What Maak takes from Make, and what it leaves behind

Maak shares Make's command line wherever the two answer the same question, so
a ~make~ habit usually lands. This is where each of Make's options ends up:

| ~make~                            | Maak                                                            |
|-----------------------------------+-----------------------------------------------------------------|
| ~-f FILE~                          | ~-f/--file FILE~, and ~./maak.scm~ when it is not given          |
| ~-C DIR~                           | ~-C/--directory DIR~, which also prints the directory it entered |
| ~-n/--dry-run~                     | ~-n/--dry-run~                                                   |
| ~-s/--silent~                      | ~-q/--quiet~ (Make's own ~-q~ asks a different question)          |
| ~-k/--keep-going~                  | ~-k/--keep-going~                                                |
| ~-i/--ignore-errors~               | ~-i/--ignore-errors~                                             |
| ~-I DIR~                           | ~-L/--load-path DIR~                                             |
| ~-h~, ~-v~                         | ~-h/--help~, ~-v/--version~                                      |
| ~-w/--print-directory~             | the default with ~-C~; ~--no-print-directory~ leaves it out         |
| ~-p/--print-data-base~             | ~--list~                                                         |
| ~--debug~                          | ~--debug~ (the Guile backtrace of the error)                     |
| ~-e/--environment-overrides~       | the environment already beats a ~.env~ file; ~-e~ is ~--env-file~ here |
| ~.DEFAULT_GOAL~                    | the ~default~ task, and a clear error when there is none          |
| ~.PHONY~                           | nothing: every task runs when it is asked to                     |
| ~MAKEFLAGS~, ~MFLAGS~              | ~MAAK_ENV_FILE~, ~MAAK_LOAD_PATH~, ~MAAK_NO_BANNER~, ~MAAK_DEBUG~  |
| ~$(shell ...)~, ~$(wildcard ...)~    | any Scheme: ~run~, ~capture~, ~$~, ~file-exists?~                  |
| ~include other.mk~                 | ~use-modules~, or ~load~ from a Maak file                        |

Three families of Make options have no counterpart, and each is a design
decision rather than an omission:

- *File targets and timestamps.*  Make decides whether to run a recipe by
  comparing the timestamps of files (~-B~, ~-t~, ~-o~, ~-W~, pattern rules,
  ~VPATH~, implicit rules).  Maak has no targets to compare and runs the task it
  was asked for; a task that wants to skip work says so itself, in Scheme, where
  the condition can be anything -- a hash, a row in a database, a check over the
  network -- and not only the age of a file.
- *Parallel jobs.*  Maak's ~-j/--jobs N~ runs up to N tasks at once, each in a
  forked worker whose output is printed as one block in the order the tasks
  were named; a task that wants to do several things inside itself uses
  Guile's own concurrency, as the test suite does with ~VERITAS_JOBS~.  Make's
  jobserver machinery and the refinements of job control (~-l~, ~-S~,
  ~--output-sync~, ~--trace~) have no counterpart: the block is the output
  synchronisation, and the number of jobs is the only control.
- *The Makefile language itself.*  Variables, ~$(...)~ expansion and the recipe
  prefixes ~@~, ~-~ and ~+~ have nothing to do here: a Maak file is Scheme, and
  a task's commands are the strings it builds.  ~-r~, ~-R~ and
  ~--warn-undefined-variables~ exist to tame built-in rules and variables that
  Maak does not have; an unbound variable is already an error with a hint.

* Parameterize: customize the running of tasks and commands

Dry-run and quietness can be defined globally using the command-line options (~-n~ / ~-q~), but they are also easily controlled and overridden in lexical scope via Lisp (Scheme) parameters.

This gives you a highly precise control mechanism when testing. For example, you can write a test task that dynamically runs destructive file manipulations safely in a localized dry-run scope, without requiring the user to pass a CLI flag.

Dry-runs for example are  good for testing.

#+begin_src scheme
(define (fmt)
  "Format Scheme source code files according to the Guix style guide."
  (syscall "ls") ;; this will run
  ;; this will not
  (parameterize ((dry-run? #t)
                 (quiet? #f))
    (delete-file-recursively "tmp")
    ($ '("find . -maxdepth 8 -name '*.scm'"
         "-type f -exec guix style -f {} \\;")
       #:verbose? #t)))
;; it will print instead or unning
;; [DRY-RUN]: rm -rfv tmp
;; [DRY-RUN]: find . -maxdepth 8 -name '*.scm' -type f -exec guix style -f {} \;
#+end_src

I personally of course like to do this with [[https://guix.gnu.org/][Guix]], [[https://www.gnu.org/software/emacs/][Emacs]], ([[https://git.sr.ht/~abcdw/emacs-arei][Arei/Ares]] + [[https://github.com/vspinu/sesman][sesman]]) you can get an ultimate extensible powerful editor experience, miles ahead of traditional IDEs 🐂 .

- *Incremental Development:* Write, test, inspect, evaluate one function or even one line at a time. Get immediate feedback without running the entire app.
- *Powerful Debugging:* Forget adding ~print~ statements and restarting. You can pause, inspect objects, change values, and even redefine a broken function on the fly to test a fix in any environment (yes even in production, while running).

When integrated into your code editor, you can execute any piece of code (a line, a selection, or a file) with a keyboard shortcut and see the result instantly, creating a seamless and powerful development experience.

** Tests

The tests live under ~test/veritas/unit~ and are written with
[[https://codeberg.org/jjba23/veritas][Veritas]].  ~maak test~ runs them; the
same run by hand is:

#+begin_src shell
VERITAS_TEST_MODULE=veritas VERITAS_TEST_TOP_DIR=test \
  VERITAS_TEST_TYPE=unit VERITAS_RUN_BENCHMARKS=false \
  guix shell -m manifest.scm -- \
  guile -L ./src -L ./test -c '((@ (veritas runner) run-tests))'
#+end_src

That has to be *this* checkout's maak, not the one an installed ~maak~ was built
with.  The maak file beside it may ask for modules a released library does not
have, and the mismatch shows up as ~no code for module (maak ...)~, which reads
like a missing file rather than as a version problem.  The launcher under
~scripts~ falls back to the sources beside it, so the checkout's own maak is one
command away, inside the environment ~manifest.scm~ declares:

#+begin_src shell
guix shell -m manifest.scm -- ./scripts/maak test
#+end_src

Every other task is reached the same way: ~-- ./scripts/maak --list~ lists them,
~-- ./scripts/maak man~ previews the manual page.

Two kinds of spec sit in that directory, and the difference is what each one can
see.  Most of them call ~main~ in process with the output ports captured, which
is how a test asserts on what a user reads while keeping a run cheap.  What that
cannot show is anything that belongs to the process rather than to the call: the
exit status an operating system sees, which of the two streams a line went to,
and the argument grammar of ~scripts/maak~ itself, which is what turns a command
line into the Guile invocation ~main~ is handed.  Those are what
~test/veritas/unit/integration.scm~ is for, running the launcher as a real
subprocess.  A suite run is the two together; nothing else starts the launcher,
and nothing else reads the library the way a caller does.

The fixtures those tests use -- a module with exports and one without, a Maak
file with failing tasks for the keep-going flags, and a directory holding a Maak
file of its own -- live under ~test/maak/fixtures~ and are deliberately kept out
of the directory the runner scans.

Three things are worth knowing when adding a test, because two of them fail
quietly rather than loudly:

- A case has to *evaluate to an assertion*, which is a procedure of one
  validation client.  A bare ~assert-*~ call is one, and so is a ~let~ whose
  last form is one.  A body that ends in ~(delete-file ...)~ is not: the case
  becomes no case at all, and the test passes without checking anything.
  Cleanup therefore belongs in a ~#:after~ hook, or in the ~after~ thunk of a
  ~dynamic-wind~ around the assertion, or before the assertion is built.
- One assertion per case.  A case is the value a form evaluates to, so an
  assertion wrapped in a body of several forms -- a ~let~ around five ~assert-*~
  calls, say -- is evaluated while the file loads and then dropped: only the
  *last* form of the body is the case that runs and can fail.  The four before
  it still run, but nothing reads their verdict, so they cannot fail the run.
  Write one assertion per form and give each one the setup it needs; a run of
  the CLI costs milliseconds, which is cheaper than a test that cannot fail.
- Anything left directly in a ~suite~, outside any ~test~, is treated as a case
  of the suite, and its result is read as though it were an assertion: the run
  then dies with "could not read assertion success from unknown type".  A
  parenthesis that closes a ~test~ a line too early is enough to do it.

The first two fail quietly, and nothing catches them for you: the run exits 0
and a test that asserted nothing passes exactly where one that asserts does.
The only sign is in the report, which prints the value of every case under the
test it belongs to -- a test with no line under it ran no case at all, and a
case showing one value where two assertions were written means one of them was
never read.  Read the report, and prefer a test that can fail to a count of
tests that passed.

* On Reproducibility: Why GNU Guix?

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
